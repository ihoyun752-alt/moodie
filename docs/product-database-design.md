# 제품 데이터베이스 설계

Moodie의 맞춤 화장품 TOP 3 추천에 쓸 제품 데이터의 컬럼 구조와 관리 기준입니다. **설계 문서이며, 아직 CSV 파일이나 실제 제품 데이터는 없습니다.**

- 작성일: 2026-10-31
- 관련 문서: `README.md`(현재 구현 상태), `docs/design.md`(디자인 기준), `docs/ideas.md`(확장 계획)
- 허용값은 사이트 코드 `js/profile-store.js`의 값과 맞춥니다. 사용자가 프로필에서 고른 값과 제품 데이터를 그대로 비교할 수 있게 하기 위해서입니다.

## 1. 설계 목적

- 실제 제품을 입력하기 전에 **컬럼 구조, 허용값, 검수 절차, null 처리 기준**을 먼저 정해, 입력하는 사람과 시점이 달라도 같은 형식으로 쌓이게 합니다.
- 추천 알고리즘(무드 40%, 퍼스널 컬러 30%, 피부 20%, 인기도 10%)이 **변환 없이 바로 읽을 수 있는 형태**로 저장합니다.
- 기존 원칙을 데이터에도 적용합니다. 사이트는 "가짜 제품이나 임의의 인기도·추천 점수를 실제 정보처럼 표시하지 않는다"(`README.md`, `docs/design.md` 9절)고 정했으므로, 확인되지 않은 값은 만들지 않고 null로 둡니다.

### 기본 방향

| 항목 | 결정 |
|---|---|
| 제품 범위 | 색조 화장품 중심 (베이스, 립, 아이, 치크). 스킨케어는 초기 범위에서 제외 |
| 초기 목표 | 실제 제품 70개 (세는 기준은 9절) |
| 관리 방식 | 통합 CSV 하나 |
| 태깅 | LLM이 초안 작성 → 사람이 검수 → 승인 |
| 추천 결과 | 개인 맞춤 화장품 TOP 3 |

## 2. CSV 공통 규칙

| 규칙 | 내용 |
|---|---|
| 인코딩 | UTF-8, 첫 줄은 컬럼 이름 |
| 한 행의 단위 | **제품의 색상(셰이드) 1개.** 같은 제품이라도 색상이 다르면 별도 행 |
| null | 빈 칸. `0`, `-`, `없음` 같은 글자로 null을 표시하지 않음 (0은 실제 값 0) |
| 여러 값 | 세로 막대 `\|`로 구분, 앞뒤 공백 없음. 예: `dry\|normal` |
| 날짜 | `YYYY-MM-DD` (예: `2026-11-03`) |
| 참/거짓 | `true`, `false`, 모르면 빈 칸 |
| 0~1 점수 | 소수 둘째 자리까지 (예: `0.8`, `0.65`). 범위 밖 값은 저장 불가 |
| 코드값 | 영문 소문자와 하이픈. 화면에 보일 한글 이름은 사이트 코드에서 붙임 |
| 쉼표·따옴표 | 값 안에 쉼표가 있으면 큰따옴표로 감쌈 (표준 CSV) |

## 4. 추가·변경한 이유

| 컬럼 | 이유 |
|---|---|
| `product_group_id` | 셰이드마다 행을 나누면 같은 제품이 여러 행이 됩니다. TOP 3에 같은 제품의 다른 색이 겹쳐 나오지 않게 하고, 제품 단위로 셀 때 필요합니다. |
| `product_id` 형식 | `MD-<제품 4자리>-<셰이드 2자리>`로 정해, 번호만 봐도 같은 제품인지 알 수 있게 했습니다. |
| `shade_code` | 셰이드 이름이 비슷하거나 언어마다 다를 때, 브랜드 번호로 정확히 구분하기 위해서입니다. |
| `price_checked_at` | 가격은 자주 바뀌므로 언제 확인한 값인지 남겨야 오래된 가격을 사실처럼 보여 주지 않습니다. |
| `hex_source` | 같은 HEX라도 공식 표기인지, 스와치 사진에서 잰 값인지에 따라 신뢰도가 다릅니다. 근거 없는 HEX를 막는 장치이기도 합니다. |
| `skin_type_caution` | "잘 맞는 피부"만으로는 "피해야 할 피부"를 표현할 수 없어, 피부 적합도 계산(8절)에서 0점을 줄 근거로 씁니다. |
| `skin_suitability` 의미 | 피부 적합도는 사용자의 피부 타입·고민에 따라 달라지므로 제품마다 값 하나로 끝낼 수 없습니다. 그래서 이 컬럼은 "사용자 정보와 무관한 기본값"으로 정하고, 실제 점수는 8절처럼 태그와 함께 계산합니다. |
| `rating_scale` | 출처마다 평점 만점이 다를 수 있어 정규화할 때 필요합니다. |
| `popularity_source`, `popularity_checked_at` | 평점·리뷰 수는 출처와 시점에 따라 달라집니다. 출처 없는 인기도를 막고, BEST 페이지의 "출처가 확인된 랭킹" 원칙(`docs/ideas.md`)과 맞추기 위해서입니다. |
| `info_checked_at` | 제품 정보가 언제 확인되었는지 알아야 다시 확인할 대상을 고를 수 있습니다. |
| `reviewed_by`, `reviewed_at`, `review_notes` | LLM 초안과 사람의 확정을 구분하고, 누가 언제 왜 승인·반려했는지 남기기 위해서입니다. |
| `is_available` | 단종 제품을 추천하지 않으면서도 기록은 지우지 않기 위해서입니다. |
| ⑦ 이미지 10개 | ALL 페이지를 사진 중심 카드로 보여 주기 위해 추가했습니다. 기존 46개 컬럼 뒤에 붙여 순서와 값을 바꾸지 않았습니다. 제품 사진과 셰이드 발색 사진은 쓰임과 근거가 달라(제품 단위 / 셰이드 단위) 따로 둡니다. 사용 허락과 일치 확인을 기록해야 권리가 확인되지 않은 사진이 공개 사이트에 올라가지 않습니다. 별도 이미지 파일 대신 이 CSV에 둔 것은 "통합 CSV 하나" 원칙을 지키기 위해서입니다. |

## 5. 허용값

### 카테고리 (`category` → `subcategory`)

| category | 의미 | subcategory |
|---|---|---|
| `base` | 베이스 | `foundation`, `cushion`, `concealer`, `primer`, `powder`, `tone-up` |
| `lip` | 립 | `lipstick`, `tint`, `gloss`, `lip-balm`(색이 있는 것), `lip-liner` |
| `eye` | 아이 | `eyeshadow`, `eyeliner`, `mascara`, `brow` |
| `cheek` | 치크 | `blush`, `highlighter`, `contour` |

- 스킨케어는 초기 범위에서 제외합니다. 메인 캐러셀의 "스킨케어" 그림은 카테고리 샘플 일러스트일 뿐이라 이 설계와 충돌하지 않습니다.
- 새 소분류가 필요하면 이 문서에 먼저 추가한 뒤 입력합니다.

### 퍼스널 컬러 (`personal_color`)

사이트 프로필의 값(`js/profile-store.js`)을 그대로 씁니다.

| 값 | 의미 |
|---|---|
| `spring-light`, `spring-bright` | 봄 웜 라이트, 봄 웜 브라이트 |
| `summer-light`, `summer-mute` | 여름 쿨 라이트, 여름 쿨 뮤트 |
| `autumn-mute`, `autumn-deep` | 가을 웜 뮤트, 가을 웜 딥 |
| `winter-bright`, `winter-deep` | 겨울 쿨 브라이트, 겨울 쿨 딥 |
| `spring`, `summer`, `autumn`, `winter` | 세부 유형은 정하기 어렵고 계절만 확인된 경우 |
| `universal` | 퍼스널 컬러와 거의 상관없는 제품 (예: 투명 프라이머, 블랙 마스카라) |

- 여러 개를 고를 수 있습니다 (`|` 구분).
- 근거가 없으면 빈 칸으로 둡니다. 색과 상관있는 제품인데 판단할 수 없으면 `universal`을 쓰지 않습니다.
- 사용자의 "아직 모르겠어요"(`unknown`)는 사용자 쪽 값이며, 제품에는 쓰지 않습니다.

### 마무리감·제형·커버력

| 컬럼 | 허용값 | 사이트 프로필과의 관계 |
|---|---|---|
| `finish` | `matte`, `semi-matte`, `satin`, `glow`, `shimmer`, `glitter` | 프로필의 선호 마무리감은 `matte`, `semi-matte`, `glow` 세 가지입니다. 이 셋은 같은 값으로 비교합니다. `satin`, `shimmer`, `glitter`는 색조 제품에 필요해 추가했고, 선호 마무리감과의 비교 방식은 알고리즘 설계에서 정합니다. |
| `texture` | `liquid`, `cream`, `powder`, `gel`, `balm`, `stick`, `pencil`, `cushion`, `water` | 프로필에는 없음 |
| `coverage` | `sheer`, `light`, `medium`, `full` | 베이스는 커버력, 립·치크·아이섀도는 발색 정도. 해당 없으면 빈 칸 |

### 피부 타입·고민 (`skin_type_tags`, `skin_type_caution`, `skin_concern_tags`)

사이트 프로필의 값을 그대로 씁니다.

|---|---|
| `skin_type_tags`, `skin_type_caution` | `dry`(건성), `normal`(중성), `oily`(지성), `combination`(복합성), `sensitive`(민감성) |
| `skin_concern_tags` | `dryness`(건조함), `oil`(유분), `pores`(모공), `trouble`(트러블), `redness`(홍조), `dullness`(칙칙함), `wrinkles`(잔주름) |

- 같은 피부 타입이 `skin_type_tags`와 `skin_type_caution`에 동시에 있으면 안 됩니다.

### 관리용 코드

| 컬럼 | 허용값 |
|---|---|
| `hex_source` | `official`(브랜드 공식 표기), `retailer`(판매처 표기), `swatch-measured`(공식·판매처 스와치 이미지에서 측정) |
| `data_source` | `official`(브랜드 공식 사이트), `retailer`(판매처), `dataset`(공개 데이터셋. 라이선스 확인된 것만) |
| `tag_source` | `llm-draft`(LLM 초안, 미검수), `llm-reviewed`(LLM 초안을 사람이 검수·수정), `human`(사람이 직접 작성), `official`(브랜드가 밝힌 정보 그대로) |
| `review_status` | `pending`(검수 대기), `approved`(승인), `needs-revision`(수정 후 재검수), `rejected`(반려, 추천에 쓰지 않음) |

### 이미지 (`product_image_type`, `swatch_image_type`)

| 값 | 뜻 |
|---|---|
| `licensed` | 브랜드에게 사용 허락을 받은 사진 (허락 근거를 `*_permission`에 기록) |
| `own-photo` | 직접 산 제품을 직접 촬영한 사진 |

- 경로는 저장소 안의 상대 경로만 씁니다 (`assets/products/<product_group_id>/…`). **외부 주소(`http…`)는 쓰지 않습니다.** 사용 허락이 확인되지 않은 공식몰 사진을 직접 연결하거나 복사하지 않기 위해서입니다.
- 제품 사진은 실제 제품 용기, 발색 사진은 그 셰이드의 실제 발색이어야 합니다. 다른 셰이드의 사진을 대신 쓰지 않습니다.
- 임시 이미지는 CSV에 적지 않습니다. 사진 칸이 비어 있으면 사이트가 자동으로 "샘플 이미지"(CSS로 그린 그림)를 보여 줍니다(8절).

## 6. 7개 무드 점수 관리

- **의미:** 해당 무드의 메이크업을 완성할 때 이 셰이드가 얼마나 잘 맞는지를 0~1로 나타냅니다. 무드끼리 합이 1일 필요는 없습니다(한 제품이 여러 무드에 잘 맞을 수 있음).
- **기준 단계:** 사람이 일관되게 판단할 수 있도록 다음 단계 중에서만 고릅니다.

| 점수 | 뜻 |
|---|---|
| `1.0` | 이 무드의 대표 제품으로 추천할 만함 |
| `0.7` | 잘 어울림 |
| `0.4` | 다른 제품과 함께 쓰면 어울림 |
| `0.1` | 거의 어울리지 않음 |
| `0.0` | 어울리지 않음 |
| 빈 칸 | 판단하지 않음 / 판단 근거 부족 |

- **판단 근거:** 무드 정의(`docs/design.md` 6절의 설명과 컬러칩, 10절의 무드별 눈 화장 기준)와 제품의 색(`hex_color`), 마무리감, 제형, 카테고리를 함께 봅니다.
- **0과 빈 칸은 다릅니다.** 0은 "어울리지 않는다고 판단함", 빈 칸은 "판단하지 않음"입니다. 계산에서는 둘 다 기여 0이지만, 검수 대상을 고를 때 빈 칸은 "아직 할 일"로 봅니다.
- **승인 전 점수는 확정값이 아닙니다.** `review_status`가 `approved`가 아닌 행의 무드 점수는 추천 계산에 쓰지 않습니다(8절).

## 7. LLM 태깅과 사람 검수 절차

1. **사람이 기본 정보 입력:** ①번 컬럼과 `hex_color`·`hex_source`, `data_source`, `info_checked_at`을 공식 출처나 판매처를 보고 입력합니다. **LLM이 제품명·가격·색 코드를 만들지 않습니다.**
2. **LLM 초안:** 기본 정보와 무드 정의를 LLM에 주고 다음을 초안으로 받습니다.
   - 7개 무드 점수
   - `personal_color`, `finish`, `texture`, `coverage`(공식 정보에 없을 때)
   - 피부 태그
   - 각 판단의 짧은 근거
   - 이 단계의 행은 `tag_source = llm-draft`, `review_status = pending`입니다.
3. **사람 검수:** 검수자는 초안을 제품 페이지, 스와치와 비교해 다음을 확인합니다.
   - 허용값만 썼는지
   - 근거가 없는 태그가 있는지 (근거가 없으면 빈 칸으로 고침)
   - 무드 점수가 6절 단계에 맞는지
   - `skin_type_tags`와 `skin_type_caution`이 겹치지 않는지
   - LLM이 실제 정보(성분, 가격, 인기도)를 지어내지 않았는지
4. **결정**
   - 승인: `review_status = approved`, `tag_source = llm-reviewed`(또는 `human`), `reviewed_by`, `reviewed_at`을 기록
   - 수정 필요: `needs-revision`과 `review_notes`. 수정한 뒤 3단계로 돌아감
   - 반려: `rejected`와 사유. 행은 지우지 않고 남김
5. **다시 검수하는 경우:** 승인된 행이라도 기본 정보(색, 셰이드, 가격)가 바뀌면 `pending`으로 되돌려 다시 검수합니다.

## 8. null 처리와 추천 알고리즘 연결

### null 처리 기준

| 상황 | 저장 방법 |
|---|---|
| 공식 색 코드가 없고 스와치 측정도 하지 않음 | `hex_color`, `hex_source` 빈 칸. **HEX를 만들지 않음** |
| 평점·리뷰 수를 출처에서 확인하지 못함 | `rating`, `review_count`, `popularity_score` 빈 칸. 0으로 쓰지 않음 |
| 트렌드 근거 없음 | `is_trending` 빈 칸 (`false`는 "확인했는데 트렌드 아님"일 때만) |
| 퍼스널 컬러·피부 태그 판단 근거 없음 | 빈 칸 |
| 가격을 확인하지 못함 | `price`, `price_checked_at` 빈 칸 |
| 필수 컬럼(브랜드, 제품명, 카테고리, 소분류, 주소, 출처, 확인일)이 없음 | 행을 승인하지 않음 (`pending` 유지) |
| 사용할 수 있는 사진이 없음 | 이미지 컬럼 10개 빈 칸. 화면에는 "샘플 이미지"(CSS 그림)를 보여 주고, 실제 제품 사진처럼 표현하지 않음 |
| 사진은 있지만 종류·허락 근거·확인일 중 하나라도 비어 있음 | 화면에 그 사진을 보여 주지 않고 샘플 이미지로 대신함 |

### 화면 표시 기준 (ALL 페이지)

- 사진은 경로·종류·허락 근거·확인일 네 칸이 모두 채워진 경우에만 보여 주고, 사진 아래에 `*_credit`을 표시합니다.
- 색상칩은 `hex_color`와 `hex_source`가 모두 있을 때만 보여 줍니다. **검증된 HEX가 없으면 칩을 숨기고, 샘플 이미지의 색도 셰이드 색처럼 보이지 않는 중립색 하나로 둡니다.**

### 점수 계산

```
최종 점수 = 0.40 × 무드 + 0.30 × 퍼스널 컬러 + 0.20 × 피부 + 0.10 × 인기도
```

- 각 항목은 0~1입니다. 항목 값이 null이면 그 항목의 기여는 0입니다.
- **가중치는 바꾸지 않고, null인 항목의 몫을 다른 항목에 나누지 않습니다.**
- **추천 대상:** `review_status = approved`이고 `is_available`이 `false`가 아닌 행만

| 항목 | 계산에 쓰는 값 | 계산 방식 |
|---|---|---|
| 무드 (40%) | 사용자가 고른 무드의 `mood_<무드>` | 값 그대로. 빈 칸이면 null |
| 퍼스널 컬러 (30%) | 사용자 프로필의 퍼스널 컬러와 `personal_color` | 세부 유형이 일치하면 1.0. 같은 계절만 일치하거나 `universal`이면 중간 점수, 아니면 0. 사용자가 `unknown`이거나 제품 값이 빈 칸이면 null. **중간 점수 값은 알고리즘 설계 단계에서 정함** |
| 피부 (20%) | 사용자 피부 타입·고민과 `skin_type_tags`, `skin_type_caution`, `skin_concern_tags`, `skin_suitability` | 사용자 피부 타입이 `skin_type_caution`에 있으면 0. `skin_type_tags`에 있으면 높은 점수. 둘 다 아니면 `skin_suitability`. 고민 태그가 겹치는 정도를 더함. 근거가 하나도 없으면 null. **세부 비율은 알고리즘 설계 단계에서 정함** |
| 인기도 (10%) | `popularity_score` | 값 그대로. 빈 칸이면 null |

- **`popularity_score` 계산 (방향만 정함):** 출처가 기록된 `rating`(`rating_scale`로 0~1 변환)과 `review_count`로 계산합니다.
  - 리뷰 수가 적어 평점이 튀는 것을 보정합니다.
  - **같은 카테고리 안에서만** 0~1로 정규화합니다.
  - 출처가 다르면 척도와 규모가 달라 섞지 않습니다.
  - 세부 공식은 실제 데이터를 확인한 뒤 정합니다.
- **TOP 3 고르기:** 최종 점수가 높은 순서로 고르되, 같은 `product_group_id`에서는 한 행(가장 점수가 높은 셰이드)만 넣습니다.
  - 점수가 같으면 null이 적은 행(근거가 많은 행)을 먼저 둡니다.
- **알려진 한계:** null이 0으로 계산되므로 데이터가 적은 제품은 불리합니다. 예를 들어 인기도 출처가 없는 제품은 최대 0.10점이 낮습니다. 가중치를 바꾸지 않는다는 원칙에 따른 것이므로, 제품별 null 개수를 검수 보고에 함께 표시해 데이터를 보강할 대상을 고르는 데 씁니다.

## 9. 실제 제품 70개 입력 기준

- **세는 단위:** 70개는 **행(셰이드) 기준**으로 셉니다. 같은 제품의 셰이드가 여러 개면 각각 1개입니다. 한 제품에 몰리지 않도록 **제품(`product_group_id`) 하나당 최대 3셰이드**로 제한합니다(제안).
- **카테고리 배분 (확정):** 무드 차이가 색으로 가장 잘 드러나는 립·아이를 많이 둡니다. 개수는 행(셰이드) 기준입니다.

  | 카테고리 | `category` 값 | 행 수 |
  |---|---|---:|
  | 립 (Lip) | `lip` | 25 |
  | 아이 (Eye) | `eye` | 20 |
  | 베이스 (Base) | `base` | 13 |
  | 블러셔 (Cheek) | `cheek` | 12 |
  | 합계 | | 70 |

  - **cheek 12개는 블러셔만 포함합니다.** 입력할 때 `category`는 `cheek`, `subcategory`는 `blush`로 씁니다.
  - 하이라이터(`highlighter`)와 쉐딩(`contour`)은 초기 70개 범위에서 **제외**합니다. 5절의 허용값에는 그대로 남겨 두는 **향후 확장 대상**입니다.

- **무드별 최소 후보 (확정):** 7개 무드(PURE, NUDE, MODERN, LOVELY, CHIC, GLAM, HIP) 각각에 대해, 승인된 행 중 무드 점수 0.7 이상인 행을 **최소 5개** 확보합니다. TOP 3를 항상 채우기 위한 기준입니다. 그중 서로 다른 제품(`product_group_id`)이 3개 이상이 되도록 하는 것은 제안 사항입니다.
- **퍼스널 컬러:** 8개 세부 유형마다 해당 셰이드가 최소 몇 개는 있도록 배분합니다(목표 수는 입력 시작 전 확정).
- **실제 존재 확인:** 행마다 `product_url`로 실제 판매·공식 페이지를 열어 브랜드, 제품명, 셰이드명이 일치하는지 확인하고 `info_checked_at`을 적습니다. 확인할 수 없는 제품은 넣지 않습니다.
- **중복 금지:** `product_id`는 중복되면 안 됩니다. 같은 브랜드·제품명·셰이드명 조합도 한 번만 넣습니다.
- **입력 순서:** 10행씩 묶어 기본 정보 입력 → LLM 초안 → 검수를 반복합니다. 묶음마다 허용값, 필수값, 범위(0~1), 날짜 형식을 검사합니다.
- **승인 비율 보고:** 묶음이 끝날 때마다 `approved` / `pending` / `needs-revision` / `rejected` 수와 컬럼별 null 비율을 기록합니다.
- **변경 기록:** 승인된 행을 고칠 때는 `review_notes`에 무엇을 왜 바꿨는지 남깁니다. `product_id`는 바꾸지 않습니다.
- **출처 이용 조건:** 공개 데이터셋이나 판매처 정보를 쓸 때는 이용 조건을 먼저 확인합니다. 확인되지 않은 출처의 값은 넣지 않습니다.
