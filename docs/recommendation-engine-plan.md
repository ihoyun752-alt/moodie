## 3. 확정 추천 규칙 (모두 사용자 결정, 2026-11-01)

### 점수
| 항목 | 규칙 |
|---|---|
| 가중치 | `점수 = 무드 × 40 + 퍼스널 컬러 × 40 + 피부 × 20` (각 항목 0~1). 인기도 제외 |
| 빈 값 | 0점으로 계산하지 않음 → 추천 대상에서 제외. 가중치를 다른 항목에 나누지 않음 |
| R1 무드 | 0~1, 단계 1.0 / 0.7 / 0.4 / 0.1 / 0.0. 빈칸 = 판단 안 함(제외). 단계 밖 값은 형식 오류 |
| R2 퍼스널 컬러 | 세부 유형 일치 1.0 · 같은 계절 다른 세부 유형 0.7 · Universal 0.7 · 다른 계절 0.0 |
| R2 사용자가 계절만 선택 | 같은 계절 제품(세부 유형 무관) 1.0 · 다른 계절 0.0 · Universal 0.7 |
| R2 제품이 계절만 표기 | 사용자는 세부 유형, 제품은 계절만이고 계절이 같으면 0.7 (예: 사용자 summer-light, 제품 summer) |
| R3 사용자 퍼스널 컬러 unknown·미입력 | 퍼스널 컬러 항목 미반영(재분배 없음). 피부 적용 제품 60점 기준, 피부 미적용 제품 40점 기준. 화면에 미반영 표시 |
| R4 피부 | 피부 = 피부 타입 × 0.5 + 피부 고민 × 0.5 |
| R4 피부 타입 | 추천 타입 포함 1.0 · 주의 타입 포함 0.0 · 둘 다 아님 0.5. 미확인이면 0.5를 주지 않고 제외. 같은 타입이 추천·주의에 동시에 있으면 데이터 오류(제외) |
| R4 피부 고민 | 일치한 고민 수 / 사용자가 고른 고민 수 |
| R4 피부 고민 미선택 | 피부 타입 점수만 피부 점수로 사용(피부 가중치 20 유지). 제외하지 않음 |
| R4 na와 빈칸 | `na` = 해당 제품에 피부 평가 미적용(제외 사유 아님). 빈칸 = 미확인(제외). 한쪽만 점수가 있으면 그 점수를 그대로 피부 점수로. 둘 다 점수가 없으면 피부 항목 미적용 |

### 추천 대상과 노출
| 항목 | 규칙 |
|---|---|
| 추천 대상 | `review_status = approved` 이고 `is_available = true`, 필요한 데이터가 검증됨 |
| R5 베이스 | approved(+ 판매 확인) 셰이드가 있는 제품만, 점수 순위 없이 전체 표시. 제품 1개 → 셰이드 1개 선택. pending은 표시하지 않음 |
| R6 노출 | 립·치크·아이섀도우 각각 추천 대상 전체 표시, 점수 높은 순. Top-K 제한 없음 |
| 동점 | 공동 순위, 경쟁 순위 방식(1위, 공동 2위, 공동 2위, 4위). 같은 점수끼리는 입력 순서로 표시(우열 아님). 동점 때문에 제외하지 않음 |
| 같은 제품 셰이드 | 셰이드별 점수 계산 → 적격 셰이드 중 최고점 셰이드를 대표로 제품당 한 번만 표시, 대표 셰이드 점수 = 제품 점수. 선택하면 대표 셰이드가 저장·결과 화면으로 전달됨 |
| 피부 적용 그룹 | 같은 카테고리 안에서 그룹 A(피부 점수 적용)와 그룹 B(피부 미적용)를 나누고, 그룹 안에서만 정렬·순위. 그룹끼리 점수·순위 비교 안 함. 화면에 그룹별 적용 기준(예: 100점, 80점, 60점, 40점) 표시 |
| 사용자 선택 | 카테고리마다 1개 |
| R7 아이섀도우 무드 | 제품마다 7개 무드 점수를 따로 관리, 여러 무드에 동시에 적합 가능. 선택한 무드의 점수로 계산. 판단 안 한 무드는 빈칸, 부적합은 0.0. 근거 없는 점수는 만들지 않음 |
| 무드 | PURE · NUDE · MODERN · LOVELY · CHIC · GLAM · HIP 7개 |

### 구현에서 정한 데이터 표기 방식 (규칙 아님, 확인 필요)
- 피부 `na` 표기 위치: 피부 타입은 `skin_type_tags = na`, 피부 고민은 `skin_concern_tags = na`.
- 피부 타입 "둘 다 아님(0.5)"은 `skin_type_tags`에 값이 있을 때만 판단. `skin_type_tags`가 비어 있으면 미확인(단, 사용자 타입이 `skin_type_caution`에 있으면 0.0으로 확정).
- `skin_suitability`는 확정 규칙에 쓰이지 않아 계산에 사용하지 않음.
- 제품 `personal_color`가 여러 개면 사용자와 가장 잘 맞는 값으로 계산.
- 같은 제품 셰이드끼리 피부 적용 여부가 다르면(그룹이 갈리면) 서로 다른 그룹 점수를 비교하게 되므로 데이터 오류로 제외.
- **셰이드 선택 (사용자 결정 2026-11-01):** 셰이드가 2개 이상인 제품 카드에 적격 셰이드만 칩으로 표시(검수 전 셰이드는 표시 안 함), 칩마다 그 셰이드 자신의 점수. 처음에는 대표 셰이드가 선택돼 있음. 다른 셰이드를 골라도 제품 순위와 카드 상단 대표 점수는 그대로. 저장·결과 화면에는 실제 고른 셰이드가 전달됨.
- 선택은 무드별로 저장. 다른 무드로 들어오면 빈 선택. 고를 수 있는 제품이 있는 카테고리만 반드시 골라야 결과로 넘어감.

## 7. v5 규칙 (2026-11-02 승인)

> 이 절이 최신입니다. 3절과 다르면 이 절을 따릅니다. 3절은 기록으로 남겨 둡니다.
> 데이터 구조는 `docs/product-database-design.md` 10절, 얼굴 색 적용은 `docs/simulation-design.md`를 따릅니다.

### 7.1 그대로 유지하는 규칙
- 가중치 `무드 40 + 퍼스널 컬러 40 + 피부 20`, 인기도 제외 (립·치크·아이섀도우)
- 빈 값은 0점이 아니라 추천 제외. 가중치를 다른 항목에 나누지 않음
- R1 무드 단계, R3 사용자 퍼스널 컬러 unknown 처리, R4 피부 계산, 동점·셰이드 대표·피부 적용 그룹 규칙
- 추천 대상: `review_status = approved`, `is_available = true`

### 7.2 무드 점수 사용 조건 (변경)
- 무드 점수는 `mood_status = approved`인 행에서만 씁니다. 그 밖의 행은 무드 점수가 있어도 "추천 데이터 미확인"으로 제외합니다.
- `data/mood-review.csv`의 제안 점수(`pending` / `hold` / `rejected`)는 엔진이 읽지 않습니다.
- `mood_status` 칸이 없는 옛 CSV(56열)는 지금처럼 `review_status`만으로 판단합니다(호환용).

### 7.3 퍼스널 컬러 (R2 확장)

사용자 값의 온도: `spring`, `autumn` 계열은 웜, `summer`, `winter` 계열은 쿨입니다.

| 제품 상태 (`docs/product-database-design.md` 10.3절) | 사용자: 세부 유형 (예: `summer-light`) | 사용자: 계절만 (예: `summer`) | 사용자: 모름·미입력 |
|---|---|---|---|
| 1 세부 유형 | 일치 1.0 · 같은 계절의 다른 세부 유형 0.7 · 다른 계절 0 | 같은 계절 1.0 · 다른 계절 0 | 퍼스널 컬러 미반영 (R3) |
| 1′ 제품 전용 유형 `summer-soft`, `autumn-soft` | 같은 계절 0.7 (일치로 보지 않음) · 다른 계절 0 | 같은 계절 1.0 · 다른 계절 0 | 미반영 |
| 2 계절만 | 같은 계절 0.7 · 다른 계절 0 | 같은 계절 1.0 · 다른 계절 0 | 미반영 |
| 3 쿨·웜만 (`cool`, `warm`) | **세부 유형과 비교할 수 없는 제품으로 별도 관리.** 0.7점·0점 등 어떤 점수도 주지 않음 (7.3.1) | **별도 관리, 점수 없음** (7.3.1) | 미반영 |
| 4 neutral | **퍼스널 컬러 미반영, 중립 그룹 (N1)** | **퍼스널 컬러 미반영, 중립 그룹 (N1)** | 미반영 (중립 그룹을 따로 만들지 않음) |
| 5 universal | 0.7 | 0.7 | 미반영 |
| 6 미확인 | 추천 제외 ("추천 데이터 미확인") | 추천 제외 | 추천 대상 (퍼스널 컬러 미반영) |

- 제품 값이 여러 개면 사용자와 가장 잘 맞는 값을 씁니다(기존과 같음).
- `personal_color`가 비어 있고 `tone_temperature = neutral`일 때만 상태 4입니다. `personal_color`에 값이 있으면 그 값으로 계산합니다.
- `personal_color`의 계절·온도와 `tone_temperature`가 서로 맞지 않으면 데이터 오류로 제외합니다.
- 상태 1′(`summer-soft`, `autumn-soft`)의 점수는 새 값을 만든 것이 아니라 기존 R2 규칙(같은 계절의 다른 세부 유형 0.7, 사용자가 계절만 고르면 같은 계절 1.0)을 그대로 적용한 것입니다.

#### 7.3.1 미승인 제안 (확정 규칙 아님, 엔진에 넣지 않음)

| 번호 | 제안 | 상태 |
|---|---|---|
| P1 | 상태 3(쿨·웜만 확인) 제품: 사용자와 온도가 같으면 0.7, 반대면 0. 근거: "제품 정보가 사용자 정보보다 덜 구체적이면 0.7"이라는 기존 R2 원칙을 적용 | **미승인** (2026-11-02 담당자 보류) |

- **확정 (2026-11-02):** P1의 점수 규칙은 확정하지 않습니다. 상태 3 제품은 "세부 유형과 비교할 수 없는 제품"으로 별도 관리하고, 0.7점이나 0점 같은 점수를 주지 않습니다. 화면 처리 방법은 엔진 단계에서 따로 승인받습니다.

**보완 규칙 (2026-11-02 확정)**
- `universal`은 다른 퍼스널 컬러 값과 함께 쓰지 않습니다. 함께 있으면 데이터 오류입니다.
- `tone_temperature = neutral`인 행에 계절·세부 유형·쿨·웜 태그가 함께 있으면 데이터 오류로 표시합니다. 임의로 고치지 않습니다.

### 7.4 뉴트럴 그룹 (N1)
- neutral 제품은 퍼스널 컬러 점수를 받지 않습니다. **고정 점수를 주지 않습니다.**
- 일반 순위와 섞지 않고 "퍼스널 컬러 중립(neutral) 제품" 그룹으로 따로 보여 줍니다. 그룹 안에서만 정렬·순위를 매기고, 그룹 제목에 실제 적용한 만점 기준(예: 무드 40 = 40점 기준)을 표시합니다.
- 그룹은 `퍼스널 컬러 적용 여부 × 피부 적용 여부`로 나뉩니다. 그룹끼리는 점수·순위를 비교하지 않습니다.
- 사용자가 퍼스널 컬러를 모르면 모든 제품이 퍼스널 컬러 미반영이므로 중립 그룹을 따로 만들지 않습니다.

### 7.5 베이스 추천 (R5 대체)

| 항목 | 규칙 |
|---|---|
| 점수 | `피부 타입 × 50 + 피부 고민 × 50` (100점 기준). 무드·퍼스널 컬러는 쓰지 않음 |
| 피부 타입 | 추천 타입 1.0 · 주의 타입 0 · 둘 다 아님 0.5 (R4와 같음) |
| 피부 고민 | 일치한 고민 수 ÷ 사용자가 고른 고민 수. 사용자가 고르지 않은 고민은 계산하지 않음(가산·감점 없음) |
| 고민 미선택 | 피부 타입 × 100 |
| A그룹 | 피부 타입과 피부 고민 정보가 모두 확인된 제품 |
| B그룹 | 피부 타입 정보만 확인된 제품. 피부 타입 × 100으로 계산 |
| 미확인 목록 | 피부 타입 정보가 없는 제품. **점수·순위를 만들지 않고** 이름만 "피부 정보 미확인"으로 표시. 부적합으로 표시하지 않음 |
| 그룹 비교 | A·B그룹은 점수로 서로 비교하지 않음 |
| 고민 미선택 사용자 | 두 그룹 모두 피부 타입 × 100으로 계산하되, **A·B그룹을 합치지 않고 나눈 채로 보여 줌** (7.5.1, P2 반려) |
| 셰이드 | 점수는 제품 단위로 매기고 셰이드는 사용자가 고름. 제품 안에서 셰이드끼리 피부 정보가 다르면 데이터 오류 |
| 추천 대상 | `review_status = approved`, `is_available = true` |
| "모든 피부" | `docs/product-database-design.md` 10.4절. 민감성 사용자는 "둘 다 아님" 0.5 |

#### 7.5.1 미승인 제안 (확정 규칙 아님)

| 번호 | 제안 | 상태 |
|---|---|---|
| P2 | 사용자가 피부 고민을 고르지 않으면 A·B그룹이 같은 식(피부 타입 × 100)으로 계산되므로 한 목록으로 합쳐 보여 줌 | **반려 (2026-11-02).** 고민을 고르지 않아도 A·B그룹은 합치지 않음 |

- "모든 피부" 제품을 민감성 사용자가 보면 0.5가 되는 것은 새 규칙이 아니라 기존 R4(추천 타입에도 주의 타입에도 없으면 0.5)를 적용한 결과입니다.

### 7.6 무드별 부족 안내
- 선택한 무드에서 카테고리의 추천 대상이 0개면 "이 무드에 맞는 검수된 제품이 아직 없어요"라고 안내합니다. 점수가 낮아서 빠진 것처럼 표시하지 않습니다.
- 목표: 무드마다 0.7 이상 셰이드 5개 이상(`docs/product-database-design.md` 9절). 근거 없는 점수로 채우지 않습니다.

### 7.7 테스트 기준 (필수 13개)
1. 퍼스널 컬러만 바꾸면 립·치크·아이 추천 결과가 달라짐
2. 피부 타입·고민만 바꾸면 베이스 순위가 달라짐
3. 무드만 바꾸면 추천 결과가 달라짐
4. 출처가 다른 근거끼리 덮어쓰이지 않음 (`evidence.csv` 기존 줄, `*_source` 칸 보존)
5. 미승인 무드 점수가 추천에 반영되지 않음
6. neutral, universal, 미확인 제품이 서로 다르게 처리됨 (퍼스널 컬러 상태 6가지 모두 확인)
7. 베이스 미확인 제품이 점수·순위를 받지 않음
8. "모든 피부" 제품이 민감성 사용자에게 1.0을 받지 않음
9. 고른 `product_id`와 얼굴에 적용된 색이 일치함
10. 색상 미확인 셰이드가 다른 색으로 칠해지지 않음
11. 원본 얼굴 이미지 파일이 바뀌지 않음
12. `products.csv`의 기존 56열 값이 모두 보존됨
13. 새 칸이 없는 CSV와 새 칸이 있는 CSV를 모두 정상적으로 읽음

### 7.9 0개 문제 해결 결정 (2026-11-02, 구현됨)

> 7.1·7.3·7.5절과 다르면 이 절을 따릅니다.

| 항목 | 결정 |
|---|---|
| 가중치 | **무드 40 · 퍼스널 컬러 30 · 피부 30.** 인기도는 점수·정렬·후보 선정·동점 처리에 쓰지 않음 |
| 카테고리별 항목 | 립·치크·아이: 무드 + 퍼스널 컬러 (**피부 미적용**). 베이스: 무드 + 퍼스널 컬러 + 피부 |
| 환산 | 실제로 적용한 항목의 가중치 합을 100점으로 환산. 예: 립 = (무드×40 + 퍼스널 컬러×30) ÷ 70 × 100 |
| 피부 미적용과 미확인 | 색조 제품의 피부 칸이 비어 있어도 제외하지 않음(미적용). 베이스의 피부 정보가 없으면 **미확인 목록**(점수·순위 없음) |
| 퍼스널 컬러 미확인 제품 | 추천에서 빼지 않고 **"퍼스널 컬러 정보 미확인 제품" 그룹**으로 따로 보여 줌. 퍼스널 컬러 점수는 계산하지 않음. 카드와 결과 화면에 "퍼스널 컬러 정보가 확인되지 않은 제품입니다." 표시. (7.3 표의 "상태 6: 추천 제외"를 대체) |
| 상태 3 (쿨·웜만) | "쿨·웜만 확인된 제품" 그룹. 퍼스널 컬러 점수 없음(P1 미확정 유지) |
| 그룹 | 퍼스널 컬러 그룹(점수 적용 / 사용자 모름 / 쿨·웜만 / neutral / 미확인) × 베이스 피부 그룹(A / B). 그룹끼리 점수·순위를 비교하지 않음 |
| 제외 사유 | 섹션마다 "추천에서 제외된 셰이드 · 사유 보기"로 셰이드별 사유를 보여 줌 |
| 데모 | 무드 점수가 승인된 셰이드 5개(MD-0001-02, MD-0004-01, MD-0005-01·02, MD-0034-01)를 데모 진행 상태(`data/demo-overlay.csv`)에 추가. 제품 특성 값은 바꾸지 않음 |

- 베이스는 무드 점수도 필요합니다. 지금은 승인된 베이스 무드 점수가 없어서, 피부 정보가 확인되더라도 "승인 무드 점수 없음"으로 제외됩니다. 베이스 무드 점수 정책은 아직 정하지 않았습니다.

## 9. v7: 색감 근거 보완 후보·검수 후보 (2026-11-02 구현)

> 이 절이 최신입니다. 8절(v6)의 무드 태그·점수 규칙은 그대로 두고, **무드 태그를 새로 승인하지 않으면서** 공식 색상 설명(`color_note`)으로 후보를 넓히는 규칙을 추가했습니다.

### 9.1 추가된 후보 구분

| 구분 | 조건 | 화면 | 점수·순위 | 선택 |
|---|---|---|---|---|
| 추천(scored) | `review_status=approved`, `is_available=true`, 고른 무드가 승인된 대표·보조 무드에 있음 | 추천 카드 | 있음 | 가능 |
| 색감 근거 보완 후보 | 승인·판매 중, 무드 태그는 다른 무드로 승인됨, `color_note`에 고른 무드의 색 단어가 있음, 퍼스널 컬러 비교 가능 | "색감 근거 보완 후보" 카드 | **없음** | 가능 |
| 검수 후보 | 승인·판매 중이지만 승인된 무드 태그가 없음 | "검수 후보" 목록(추천 제외) | 없음 | 불가 |

- **무드 태그를 새로 승인하지 않습니다.** 보완 후보는 기존 `mood_primary`·`mood_secondary`를 덮어쓰지 않고, 공식 색상 설명이 고른 무드의 색감과 맞는지만 보여 줍니다.
- **제품 검수 승인과 무드 태그 승인은 별개입니다.** 화면에 `제품 검수: 승인 · 판매 중 / 무드 태그: 미승인 (승인된 태그: …)`처럼 두 상태를 나눠 표시합니다.
- 검수 후보는 추천 카드·선택지에 넣지 않습니다. `MD-0013-02`(로지킴 로즈프레소), `MD-0030-03`(투에이엔 멜로우 로즈)이 여기에 해당합니다.
- 색감 단어는 `js/recommend-engine.js`의 `COLOR_EVIDENCE` 키워드 맵으로만 판정합니다. 예: NUDE = 누드·누디·베이지·애프리콧·샌드·차분한 / LOVELY = 로지 등 / CHIC = 모브 등 / GLAM = 골드 등.
- 색상값(HEX)이 없어도 후보가 될 수 있지만, 시뮬레이션에는 적용하지 않습니다. 후보 색은 `data/color-approval-candidates.csv`에 `no-hex`·`pending`으로 기록했습니다.

### 9.3 무드별 후보 수와 실제 추천 카드 수가 다른 이유

1. **같은 제품의 셰이드 대표화:** 같은 `product_group_id`와 같은 퍼스널 컬러·피부 그룹이면 정렬 기준이 가장 앞선 셰이드 1개만 카드가 됩니다. 예: LOVELY 립은 승인 태그 2행(`MD-0005-01`·`MD-0005-02`)이지만 같은 `MD-0005`라 카드 1개이고, `MD-0005-02`는 셰이드 선택지에 남습니다. PURE·LOVELY 아이도 `MD-0030-01`·`MD-0030-02`가 같은 제품이라 카드 1개입니다.
2. **퍼스널 컬러 그룹이 다르면 같은 제품도 따로 셈:** LOVELY 치크는 5행(`MD-0013-01`, `MD-0014-01`, `MD-0015-01`, `MD-0015-02`, `MD-0016-01`)이고, `MD-0015-01`(뉴트럴)과 `MD-0015-02`(웜)가 다른 그룹이라 카드도 5개입니다.
3. **보완·검수는 카드 수에 포함하지 않음:** NUDE 치크의 실제 추천 카드는 2개이고, 로지킴 멜로우를 포함한 보완 후보 2개와 검수 후보 1개가 별도로 표시됩니다.
4. **데이터가 없으면 0개:** MODERN·HIP 립과 GLAM·HIP 아이는 승인된 무드 태그가 있는 셰이드가 없어 0개입니다. 엔진이 낮은 점수로 숨긴 것이 아닙니다. MODERN 립은 `MD-0012` 로지킴 립 3개가 모두 `review_status=pending`이라 후보가 될 수 없습니다.

### 9.5 립·아이 처리

- 승인 립 6셰이드(`MD-0001-01`·`02`·`03`, `MD-0004-01`, `MD-0005-01`·`02`)는 모두 퍼스널 컬러 정보가 없습니다. 엔진은 이를 **"퍼스널 컬러 정보가 부족한 제품" 그룹**에 넣고 무드로만 순위를 매깁니다. PC 정보가 없다는 이유로 제외하지 않습니다.
- 실제 PC 불일치는 **"추천" 그룹 안에서 PC 점수 0점(다른 계절)** 으로 표시됩니다. 정보 부족(비교 불가)과 불일치(비교했지만 0점)를 같은 것으로 합치지 않습니다.
- 승인 아이 6셰이드 중 `MD-0030-03`은 `review_status=approved`이지만 `mood_tag_status`가 비어 있어 **검수 후보**입니다. 제품 승인과 무드 태그 승인을 구분한 예입니다.
- `MD-0032-02`는 공식 `color_note`가 없습니다. 기존 공식 조사 자료(`docs/eyeshadow-product-research.md` 45행)에서 확인되는 것은 **칸 이름 10개**뿐이며, 색상값은 없습니다. 이 10개를 `data/palette-colors.csv`에 `status=name-only`로 기록했고 시뮬레이션에는 적용하지 않습니다.
- `MD-0034-01`은 공식 조사 자료의 칸별 측정 참고값 10개를 `status=reference`로 표시하지만, 시뮬레이션에는 승인된 메인 1색 `#BF896D`만 사용합니다.

### 9.7 남은 데이터 부족

- **치크 색상값이 없습니다.** 승인 치크 10셰이드 모두 `hex_color`·`swatch_image`가 비어 있고, 공식 조사 자료에는 색상 설명 문구만 있습니다. 그래서 치크는 양쪽 볼 마스크가 있어도 실제 색을 적용할 수 없고, 결과 화면에 "색상 검수 전 · 적용 안 함"으로 표시됩니다. `data/color-approval-candidates.csv`에 승인 후보를 `pending`·`no-hex`로 남겼습니다. 공식 발색 이미지 측정값이나 담당자 승인 HEX가 있어야 적용할 수 있습니다.
- `MD-0013-02`는 색상 설명·무드 태그가 모두 없어 `hold`입니다.
- `MD-0032-02`는 칸 이름만 확인되어 색상값 승인이 필요합니다.
- 로지킴 립 3개(`MD-0012-01`·`02`·`03`)는 `review_status=pending`이라 MODERN 립 0개에 기여하지 못합니다.
